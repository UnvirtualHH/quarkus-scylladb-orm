# Review quarkus-scylladb-orm — 2026-09-08

Anlass: Upgrade auf Quarkus 3.39.2 (von 3.36.1), im Zuge dessen ein erneuter
Durchgang durch Runtime, Annotation Processor, Deployment-Modul, POMs und CI.

Stand: Commit `5fc6f58` (Merge PR #1), Branch `main`.
Vorgänger-Review: [REVIEW-2026-08-04.md](REVIEW-2026-08-04.md).

---

## Kurzurteil

**Das Upgrade selbst ist ereignislos.** 3.36.1 → 3.39.2 ist ein reiner
Property-Wechsel, kein API-Bruch, keine Anpassung an Build-Steps oder
Config-Mapping nötig. Der volle Build läuft durch.

Die Substanz dieses Durchgangs liegt woanders: der August-Review hat die
Laufzeitpfade gründlich abgeklopft, aber die **Fehlerpfade des Annotation
Processors** blieben dünn getestet — und genau dort liegen zwei Bugs, die
generierten Code erzeugen, der nicht kompiliert bzw. gar nicht erst entsteht.
Dazu ein Binding-Bug, der eine dokumentierte API unbenutzbar macht, und zwei
Konfigurations-Fallen, die *fail-open* sind: sie schalten still ab, was man
gerade eingeschaltet hat.

Keine Injection-Lücke gefunden. Die Stellen, an denen Strings in CQL landen
(`Sortable`, Strukturparameter `:limit`/`:order`), sind sauber validiert; die
Guards sind angemessen eng und die Regexe halten dem Blick stand.

Alle unten aufgeführten Befunde sind gefixt und mit Regressionstests belegt.

## Befunde

### B1 — Ein mehrfach verwendeter `:name` erzeugt nicht kompilierbaren Code

**Schwere: hoch** (Build bricht, Fehlermeldung zeigt auf generierten Code)

```java
@Query(name = "byRange", cql = "SELECT * FROM t WHERE seen >= :ts AND touched >= :ts")
```

erzeugte

```java
public Sample byRange(Object ts, Object ts) { ... }   // javac: Variable ts ist bereits definiert
```

Denselben Parameter zweimal zu binden ist eine völlig normale Sache
(`created >= :ts AND updated >= :ts`), und die Argumentliste war sogar richtig —
nur die Signatur nicht. Der Fehler landet in generiertem Code, den man nicht vor
sich hat.

**Fix:** Die Signatur wird aus den *distinct* Namen gebaut, die Binding- und
`String.format`-Argumentlisten bleiben pro Marker.
[QueryMethodFactory.java](runtime/src/main/java/io/quarkiverse/quarkus/scylladb/orm/processor/QueryMethodFactory.java)

### B2 — Projektionen können keine Collection-Spalten lesen

**Schwere: hoch** (Build bricht, Meldung nennt weder Query noch Feld)

Ein `@Query(resultClass = ...)` auf ein Record/DTO mit einem Feld
`List<String>` scheiterte an
`ClassName.bestGuess("java.util.List<java.lang.String>")`:

```
error: Failed to generate query method for @Query: not a valid name: List<java
```

Die Query wurde stillschweigend fallengelassen, die Meldung nannte weder den
Query-Namen noch das Feld.

**Fix:** `List`/`Set`/`Map` gehen über die typisierten `Row`-Accessoren
(`getList`/`getSet`/`getMap`) — genau wie im Entity-Mapper und ohne
Reflection, also native-tauglich. Alles andere Parametrisierte bricht weiterhin
ab, aber mit einer Meldung, die Spalte und Typ nennt. Die
`@Query`-Fehlermeldung nennt jetzt generell den Query-Namen.

### B3 — Ein einzelnes `Map`-Argument war nie als Wert bindbar

**Schwere: hoch** (dokumentierte API in einem Fall unbenutzbar)

`StatementBinder.bind` entschied allein am Typ des Arguments:

```java
if (params.length == 1 && params[0] instanceof Map<?,?> map) return bindNamed(...);
```

Damit ist

```java
repository.execute("UPDATE profile SET attributes = ? WHERE id = ...", Map.of("locale", "fr"));
```

nicht ausdrückbar: die Einträge der Map wurden als *Parameternamen* gelesen, der
Treiber lehnte den ersten unbekannten ab. Betroffen ist jedes Statement mit genau
einem Marker über einer `map<,>`-Spalte — in einem Schema mit Map-Spalten keine
exotische Konstellation.

**Fix:** Nicht der Typ des Arguments entscheidet, sondern das Prepared
Statement: als benannte Parameter gilt eine Map nur, wenn *alle* ihre Schlüssel
tatsächlich Parameternamen des Statements sind. `query(cql, Map.of("name","John"))`
verhält sich unverändert.
[StatementBinder.java](runtime/src/main/java/io/quarkiverse/quarkus/scylladb/orm/repository/StatementBinder.java)

> Der Rest-Fall bleibt mehrdeutig: eine einelementige Map, deren Schlüssel exakt
> so heißt wie der einzige Marker. Der löst weiterhin nach *named* auf — wie
> bisher, also ohne Regression. Sauber wäre eine explizite API
> (`queryNamed(cql, Map)`); das ist ein API-Zusatz und gehört in eine eigene
> Entscheidung, siehe *Offen*.

### B4 — Ein Tippfehler im Throttler-Typ schaltet die Überlastsicherung ab

**Schwere: mittel** (fail-open, Security/Availability)

`quarkus.scylla.throttler.type=concurency` fiel in den `default`-Zweig und damit
auf den `PassThroughRequestThrottler`. Der Schutz, den man gerade konfiguriert
hat, war schlicht nicht da — und nichts sagte es. Bei 20M writes/day merkt man
das erst, wenn der Cluster schon steht.

**Fix:** `normalizeThrottlerType` akzeptiert `none`/`concurrency`/`rate` und
wirft sonst beim Start, mit dem falschen Wert und den gültigen in der Meldung.

### B5 — `Pageable` mit Größe 0 macht aus Paging einen Full-Table-Read

**Schwere: mittel** (fail-open)

`Pageable.ofSize(0)` wurde durchgereicht bis `setPageSize(0)`, und das liest der
Treiber als *kein* Paging: `findAllPaged` holte die ganze Tabelle in einer Seite.
Das genaue Gegenteil des Aufrufs, und unsichtbar bis zum Coordinator-Timeout.

**Fix:** Der Record lehnt `size < 1` im Kompakt-Konstruktor ab.

### B6 — `Multi`-Reads ignorierten Backpressure

**Schwere: hoch** (unbegrenztes Puffern unter Last)

`executeQueryForList` und `projectionMulti` bauten über
`Multi.createFrom().emitter(...)` und schoben in `emitAllPages` jede Zeile jeder
Seite hinein, so schnell der Treiber liefern konnte. Geprüft wurde nur
`isCancelled()`, **nie `requested()`** — im ganzen `runtime/src/main` kam weder
`requested()` noch `onRequest` noch `emitOn` vor.

Der Emitter-Default ist `BackPressureStrategy.BUFFER` mit
`overflowBufferSize = -1`, und in `BufferItemMultiEmitter.emit` heißt das:
unbegrenzte Queue, Bound-Check per Kurzschluss übersprungen, kein
`BackPressureFailure`. Nachgestellt mit der Emissionsform von `emitAllPages`
(200 Seiten à 5000 Zeilen) und einem Subscriber, der genau ein Item anfordert:

```
demand at first emit : 1
rows emitted         : 1000000
rows consumed        : 1
rows buffered        : 999999
```

Kein Fehler, kein Abbruch. Die Abrufrate hing am Netzwerk, nicht am Verbrauch —
und ein `Multi` statt `Uni<List<T>>` zurückzugeben ist genau das Versprechen,
inkrementell mit beschränktem Speicher konsumieren zu können.

Betroffen waren `findAll()`, `query(...)`, `queryProjectionList` und alle
generierten reaktiven `@Query`-Methoden mit `ReturnType.LIST`. Nicht betroffen:
`findAll(Pageable, Sortable)` (eine Seite, `Multi.createFrom().iterable` ist
demand-getrieben) und alles, was `Uni` liefert.

**Fix:** Die Emitter sind weg. Seiten kommen aus einem demand-getriebenen
`Multi.createBy().repeating().uni(...).whilst(AsyncResultSet::hasMorePages)` —
`repeating().uni` subscribed die erzeugte `Uni` (und führt damit den Fetch aus)
erst bei Demand. Das Flachklopfen auf Zeilen läuft über
`transformToMultiAndConcatenate`, das den Demand durchreicht, statt vorauszulesen.

Ein Detail, das leicht danebengeht: der zustandsführende
`uni(Supplier, Function)`-Overload hält **einen** Zustand für die Lebensdauer der
`Uni`, nicht pro Subscription — ein zweiter Subscriber würde dort weitermachen,
wo der erste aufgehört hat. Deshalb steckt das Ganze in
`Multi.createFrom().deferred(...)`, das pro Subscriber einen frischen Cursor
anlegt. Ein Test deckt genau das ab.

Fehlersemantik unverändert: Query- und Fetch-Fehler bleiben
`ScyllaQueryException`, Mapping-Fehler `ScyllaMappingException` — die
Transformation sitzt oberhalb der Zeilenstufe, damit ein Mapping-Fehler nicht
umetikettiert wird.

Zwei Randfälle sind mitgetestet, weil sie bei Scylla real vorkommen: leere Seiten
mitten im Ergebnis (gefilterte Scans) dürfen den Stream nicht anhalten, und der
Demand muss über sie hinweg getragen werden.

> Unverändert: emittiert wird auf einem Treiber-I/O-Thread (gemessen: `s1-io-5`).
> Wer im Consumer blockiert oder rechnet, braucht `emitOn` — steht jetzt in der
> README.

**Performance:** gegengemessen mit einer synthetischen Bank (Fake-Seitenquelle,
1M Zeilen, alte gegen neue Operator-Kette, Median aus 5 Läufen nach Warmup):

| Szenario | alt | neu |
|---|---|---|
| ohne Arbeit pro Zeile | 12 ms | 4 ms |
| leichte Arbeit pro Zeile | 16 ms | 10 ms |
| 200 µs Fetch-Latenz pro Seite | 563 ms | 550 ms |
| Consumer nimmt 10 von 1M Zeilen | 1999/2000 Seiten geholt, 117 MB gehalten | 0 Seiten, 11 MB |

Die Durchsatzdifferenz sind ~6–8 ns pro Zeile — gegen Deserialisierung im
Treiber und das Entity-Mapping, die einen echten Read dominieren, ist das
Rauschen. Die belastbare Aussage ist **keine Regression**, nicht „doppelt so
schnell".

Die naheliegende Sorge, der Wegfall des (unbeabsichtigten) Read-Aheads koste
Wall-Clock, hat sich nicht bestätigt: unter unbegrenztem Demand liefert
`BufferItemMultiEmitter.drain()` synchron im Emit-Loop aus, die alte Variante
war also ebenfalls streng sequentiell Fetch → Emit → Fetch. Der Latenz-Fall oben
zeigt genau das (0,98x).

Der `PagedMultiTest` zählt Seiten-Fetches und ist damit ein deterministischer
*Verhaltens*-Guard gegen einen Rückfall — keine Durchsatzmessung. Die fehlte im
Projekt komplett und ist jetzt nachgezogen, siehe unten.

### S1 — `auto-service` zog vier Jars in jede Anwendung

**Schwere: niedrig** (Angriffsfläche / Abhängigkeitshygiene)

`com.google.auto.service:auto-service` stand auf `compile` scope. Gebraucht wird
es nur, um die `@AutoService`-Annotation am Prozessor zu übersetzen — die
`META-INF/services`-Datei schreibt der unter `annotationProcessorPaths`
konfigurierte Prozessor. Auf `compile` landeten `auto-common`, `failureaccess`,
`jspecify` und `error_prone_annotations` im Runtime-Classpath jeder Anwendung,
die diese Extension benutzt.

**Fix:** `provided`. Verifiziert, dass die Service-Datei weiterhin im Jar liegt.

`javapoet` bleibt bewusst auf `compile`: der Prozessor liegt im Runtime-Artefakt
und wird beim Build der *Anwendung* per ServiceLoader gefunden, braucht javapoet
also auf deren Compile-Classpath.

### S2 — CI-Workflows ohne `permissions`-Block

**Schwere: niedrig** (Härtung)

Beides sind `pull_request`-Workflows (nicht `pull_request_target`) und
interpolieren keinen untrusted Input in `run:` — das ist sauber. Aber ohne
expliziten `permissions:`-Block gilt der Repo-Default, der bei älteren
Repositories `contents: write` ist. Kein Schritt schreibt ins Repository.

**Fix:** `permissions: contents: read` in beiden Workflows.

### Kleinkram (mitgefixt)

- `detectStoreType` benutzte `toLowerCase()` ohne Locale — das Default-Locale
  darf nicht entscheiden, wie ein Dateipfad gelesen wird.
- Ungenutzte Locals `pkNames`/`ckNames` in `delete`/`exists` beider
  Repository-Klassen. Nicht nur Rauschen: `getPartitionKeyNames()` gibt
  `.clone()` zurück, das war eine Array-Allokation pro `delete()`.
- `ReactiveRepository.concat` war tot (die reaktive Klasse hat kein
  `query(cql, Pageable, Sortable, …)`).

## Geprüft und in Ordnung

Damit klar ist, was nicht nur ungelesen blieb:

- **CQL-Injection.** `Sortable` validiert gegen `^[a-zA-Z_][a-zA-Z0-9_]*$` im
  Kompakt-Konstruktor; die Strukturparameter `:order`/`:sort`/`:orderby` gegen
  `^ident\s+(ASC|DESC)$`, `:limit`/`:offset` gegen `^\d+$` — und zwar im
  *generierten* Code, vor `String.format`. `String.matches` verlangt den
  Vollmatch, das nachgestellte `$` öffnet also keine Zeilenumbruch-Lücke. Alles
  andere geht über Prepared Statements.
- **Der DDL-Guard** (`SCHEMA_OR_TRUNCATE_LEADING`) ist korrekt am führenden
  Verb verankert, greift also nicht auf `WHERE action = 'DROP'`.
- **Exception-Hygiene.** `describeParams` gibt Anzahl und Typen aus, nie Werte.
  Das hält für alle vier Exception-Klassen.
- **TLS.** `ProgrammaticSslEngineFactory` mit `hostnameValidation` (Default
  `true`) — nicht `withSslContext`, das Hostname-Prüfung abschaltet. Keystore-
  und Truststore-Pfade werden getrennt behandelt, Passwörter als `char[]`.
- **Least Privilege.** Der Superuser-Warnhinweis und die Auth-Paar-Validierung
  aus der Juni-Runde stehen und sind getestet.
- **Keine Secrets im Repository**, `.gitignore` deckt die Release-Artefakte ab.
- **Deployment-Modul.** Die Native-Registrierungen sind konservativ und prüfen
  vor `RuntimeInitializedClassBuildItem` die tatsächliche Runtime-Abhängigkeit.

## Offen

Bewusst nicht angefasst, in absteigender Relevanz:

1. **Explizite API für benannte Parameter** (`queryNamed(cql, Map)`), damit die
   Rest-Mehrdeutigkeit aus B3 verschwindet statt nur schmaler zu werden.
2. **Native-Build gegen 3.39.2** — läuft nur im eigenen Workflow.
3. **Degradiertes Cluster-Verhalten** (Timeouts, Node-Ausfall, Throttler-Ablehnung
   unter Last) ist weiterhin ungetestet. Stand schon im August-Review.
4. **`update()` auf einer Entity mit null-`@GeneratedValue`-PK** erzeugt still
   eine zufällige UUID und schreibt damit eine neue Zeile. Formal „garbage in",
   praktisch eine Datenfalle.
5. **`@Table`-Wert und Keyspace** landen ungeprüft in jedem generierten
   Statement. Compile-Zeit-Input des Entwicklers, kein Injection-Kanal — eine
   Validierung würde nur die Fehlermeldung verbessern und riskiert, quoted
   Identifier abzulehnen.

## Performance-Tests (neu)

Das Projekt hatte **keinerlei** Performance-Messung — kein JMH, kein Benchmark,
keine Durchsatz- oder Latenzzahl. Für eine Library mit 20M writes/day als Ziel
war das nach den Funktionstests die auffälligste Lücke. Zwei Ebenen sind jetzt
da, bewusst mit unterschiedlichem Anspruch:

**`benchmarks/` — JMH, ohne DB.** Misst die Schicht, die dieses Projekt selbst
schreibt: die generierten Mapper und die Streaming-Pipeline. Kein Netzwerk, kein
CDI, ein Fake-`Row`, damit die Zahlen zwischen Commits vergleichbar sind. Das
Modul wird von jedem Build kompiliert (kann also nicht verrotten), aber nie von
`mvn verify` ausgeführt. CI fährt es wöchentlich und auf Zuruf und hebt das JSON
als Artefakt auf.

Größenordnung auf einer Entwicklermaschine: `map(Row)` ~68 ns/Zeile,
`toProperties` ~56 ns/Write, Streaming ~5 ns/Zeile. Die letzte Zahl ist der
Punkt — die Pipeline, um die es bei B6 ging, ist ein kleiner Bruchteil der
Mapping-Kosten, und die sind wiederum ein kleiner Bruchteil eines echten Reads,
sobald Treiber-Decoding und Netzwerk dazukommen.

**`WriteThroughputTest` — grob, gegen echtes Scylla.** Kein Benchmark: ein
Container auf einem geteilten Runner produziert keine über Maschinen hinweg
vergleichbare Zahl. Es fängt die Klasse von Regression, die ein Mikrobenchmark
nicht sehen kann — ein zusätzlicher Round Trip pro Write, ein Prepared Statement
das nicht mehr wiederverwendet wird, verlorene Nebenläufigkeit.

Die belastbare Zusicherung ist deshalb **relational** statt absolut:
nebenläufige Writes müssen sequentielle deutlich schlagen. Gemessen 7,3x
(5.388 → 39.063 rows/s), die Schwelle liegt bei 1,33x — genug Luft für einen
gedrosselten Runner, eng genug, um „Nebenläufigkeit kommt nicht mehr beim
Treiber an" zu fangen. Getaggt `throughput`, aus dem Alltags-Build
ausgeschlossen, eigener CI-Schritt.

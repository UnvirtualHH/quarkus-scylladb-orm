# Gesamtreview quarkus-scylladb-orm — 2026-08-04

Stand: Commit `d4ca9e8` (Release 1.0.10), Branch `main`, Build grün
(`mvn -pl runtime,deployment -am test-compile`).

Umfang: 61 Java-Dateien, ~6.100 LOC, alle Module (runtime, deployment,
integration-tests, docs) plus generierte Sources und POMs.

## Kurzurteil

Der Kern — Codegen zur Compile-Zeit, keine Reflection zur Laufzeit, getrennte
blocking/reactive Repos — ist eine gute Architektur für Quarkus. Die
Security-Runde vom Juni hat echte Löcher gestopft, und die README-Sektion mit
den Betriebs-Caveats ist ehrlicher als bei den meisten OSS-ORMs.

Aber: **die Sicherheit aus "91 grüne Integration-Tests" ist zu einem großen Teil
eingebildet.** Die Tests decken genau die Feature-Fläche nicht ab, die am
meisten generierten Code enthält. Für eine Library im High-Traffic-Prod-Pfad ist
das der größte Befund — vor den Performance-Themen.

### Fortschritt

**Schritt 1 — CI (erledigt).** `.github/workflows/build.yml` (JVM-Build +
Integration-Tests gegen Testcontainers-Scylla, auf Push/PR nach `main`) und
`.github/workflows/native.yml` (Native-Build via
`quarkus.native.container-build`, auf `main` + wöchentlich + on demand).

Zwei Dinge waren nötig, damit ein nacktes `mvn verify` durchläuft:

- `-Dgpg.skip=true` im CI-Aufruf. Das `maven-gpg-plugin` hängt im Parent-POM
  **unbedingt** an der `verify`-Phase, nicht im `release`-Profil — CI hat keinen
  Signing-Key. Verifiziert, dass der Flag greift (keine `.asc`-Artefakte).
  Sauberer wäre, das Plugin ins `release`-Profil zu verschieben → als **D14**
  aufgenommen.
- `quarkus.scylla.request.timeout=15s` in `ScyllaDbTestResource`. Der
  2s-Produktionsdefault ist zu knapp für die `COUNT(*)`-Vollscans der Suite
  gegen einen einzelnen Container-Node. Vorher brauchte die Suite dafür einen
  manuellen CLI-Flag.

Baseline lokal verifiziert: `mvn -B -ntp verify -Dgpg.skip=true` → 91 Tests,
0 Failures, ~1 min.

**Schritt 2 — Test-Entities (erledigt).** Zwei neue Entities plus Tests, 91 → 110
Tests, alle grün:

- `Event` — zusammengesetzter Partition Key (2 Spalten) **und** zusammengesetzter
  Clustering Key (2 Spalten), `Instant`, `LocalDate`, `LocalTime`, `BigDecimal`,
  `BigInteger`, `ByteBuffer`. 9 Tests inkl. `findByKeys`/`exists`/`update`/`delete`
  über den vollen Composite Key und den Arity-Fehlerpfaden.
- `Profile` — `@Enumerated(STRING)`, `@Enumerated(ORDINAL)`, `List`, `Set`, `Map`,
  `@Convert`. 7 Tests.
- `MappingLimitationsTest` — 3 Characterization-Tests (siehe unten).

**Die Erwartung "das legt echte Bugs offen" hat sich für die Laufzeitpfade nicht
bestätigt.** Composite Keys, beide Enum-Modi, Collections, Converter und die
Zeit-/Zahlentypen funktionieren auf Anhieb; sie waren schlicht ungetestet. Der
generierte Code ist auch bei geschachtelten Enums (`Profile.Status`) korrekt.

Was sich dagegen **bestätigt hat** — drei Behauptungen aus dem Review, jetzt mit
Beleg statt Vermutung:

| Behauptung | Ergebnis |
|---|---|
| README-Converter-Beispiel kompiliert nicht | bestätigt, README korrigiert (`toCqlColumn`/`toEntityAttribute`) |
| `byte[]` wird nicht unterstützt | bestätigt: `CodecNotFoundException: [BLOB <-> [B]` |
| `LocalDateTime` wird nicht unterstützt | bestätigt: `CodecNotFoundException: [TIMESTAMP <-> java.time.LocalDateTime]` |
| E9: Teilspalten-SELECT in die Entity bricht | bestätigt: `IllegalArgumentException: street is not a column in this row` |

Diese vier standen als "handled automatically" bzw. gar nicht in der README. Die
Typliste ist korrigiert, die E9-Einschränkung ist jetzt dokumentiert, und alle
drei Laufzeit-Limitierungen sind über `MappingLimitationsTest` festgenagelt —
Characterization-Tests, die beim jeweiligen Fix umgedreht werden.

`LocalDateTime` bleibt bewusst nicht unterstützt (ohne Zeitzone ist die
Umrechnung mehrdeutig) — `Instant` oder `@Convert` ist die richtige Antwort.
`byte[]` dagegen ist eindeutig und lohnt Unterstützung → als **D15** aufgenommen.

**Schritt 3 — Spaltenliste statt `SELECT *` (erledigt).** `EntityMapper` bekommt
`getColumnNames()`, der `MapperGenerator` erzeugt dazu eine
`COLUMN_NAMES`-Konstante aus allen gemappten (nicht-`@Transient`) Feldern. Beide
Repositories joinen die Liste einmal im Konstruktor zu `columnList` und benutzen
sie in `findById`, `findByKeys`, `findAll()`, `findAll(Pageable, Sortable)` und
`findAllPaged` — je acht Stellen blocking und reaktiv.

Wirkung verifiziert: vor der Änderung warnte der Driver bei jedem eingebauten
Read; danach stammen alle verbliebenen Wildcard-Warnungen im Testlauf (7)
ausschließlich aus handgeschriebenem CQL in den Tests
(`personRepository.query("SELECT * FROM person")`, `@Query`-Beispiele der
Entities). Die Framework-eigenen Lesepfade sind warnungsfrei. 110 Tests grün.

Breaking: `EntityMapper` hat eine neue Methode. Nur generierte Mapper
implementieren das Interface, insofern schlägt das nur bei handgeschriebenen
Implementierungen durch — Teil des 1.1.0-Schnitts.

## Kritisch

### K1 — Die Testabdeckung deckt die riskanten Pfade nicht ab

Alle Test-Entities zusammen benutzen genau **drei Feldtypen**: `UUID`, `String`,
`Boolean`. Verifiziert:

```
grep -rn "ClusteringKey\|Enumerated\|@Convert\|List<\|Set<\|Map<\|Instant\|BigDecimal" \
     integration-tests/src/main/java/
→ NONE FOUND
```

Generiert, in der README als Feature beworben, aber **nicht getestet**:

- Clustering Keys / Composite Keys (`buildWhereClause`,
  `getClusteringKeyComponents`, `findByKeys`, `deleteByKeys`)
- `@Enumerated` — STRING **und** ORDINAL
- `@Convert` / `AttributeConverter`
- `List` / `Set` / `Map`-Felder
- `Instant`, `LocalDate`, `LocalTime`, `BigDecimal`, `BigInteger`, `byte[]`,
  `ByteBuffer`

Das ist keine Abdeckungslücke, das ist "der Code ist nie gelaufen". Zwei Belege,
dass das mehr als Theorie ist:

**a)** Das Converter-Beispiel in `README.md:572` **kompiliert nicht**. Es
implementiert `convertToDatabaseColumn` / `convertToEntityAttribute`
(JPA-Namen); das tatsächliche Interface
(`runtime/.../converter/AttributeConverter.java`) heißt `toCqlColumn` /
`toEntityAttribute`. Niemand hat den Pfad je benutzt.

**b)** Die Liste "handled automatically" in `README.md:563` enthält
`LocalDateTime` und `byte[]`. Der Driver hat für beide keinen Codec — generiert
wird `row.get("x", LocalDateTime.class)`, das wirft zur Laufzeit
`CodecNotFoundException`.

### K2 — Keine CI

Kein `.github/`, keine Pipeline. Release läuft per `maven-release-plugin` mit
GPG-Signatur vom Laptop direkt nach Maven Central. Für eine Library im Prod-Pfad
das größte *operative* Risiko im Repo: keine Build-Matrix, keine reproduzierbare
Freigabe, kein automatischer Integrationslauf gegen echte Scylla.

### K3 — Der Annotation Processor hat null direkte Tests

`runtime/.../processor/QueryMethodFactory.java` ist 750 Zeilen Regex- und
String-Manipulation, die Java-Quellcode erzeugt — die fehleranfälligste Datei im
Projekt. Getestet nur indirekt über sechs `@Query`-Beispiele in den
IT-Entities.

Konkreter Defekt daraus: `guessParamNamesFromCql`
(`QueryMethodFactory.java:408`) leitet Parameternamen aus Spaltennamen ab, ohne
auf Duplikate zu prüfen — `WHERE a = ? AND a = ?` erzeugt zwei Parameter `a` und
damit **nicht kompilierbaren generierten Code**.

Das Deployment-Modul hat ebenfalls 0 Tests — dort liegen nur zwei leere
Neo4j-Template-Stubs unter `deployment/src/test/java/.../neo4j/ogm/test/`.

### K4 — Native Image: registriert, aber nie gebaut

Rund die Hälfte von
`deployment/.../deployment/ScyllaDBOrmProcessor.java` existiert für
Native-Support; ein Native-Build wurde nie gefahren. Mindestens eine
Registrierung ist nachweislich falsch:

```java
// ScyllaDBOrmProcessor.java:243
serviceProviders.produce(new ServiceProviderBuildItem(
        "com.datastax.oss.driver.api.core.session.SessionBuilder",
        "com.datastax.oss.driver.internal.core.session.DefaultSession"));
```

`DefaultSession` implementiert `SessionBuilder` nicht — `SessionBuilder` ist
eine abstrakte Klasse, kein Service-Interface. Das schreibt einen kaputten
`META-INF/services`-Eintrag ins Image.

## Ernst

### E5 — Der ID-Typ ist immer `Object`

```java
// generiert:
public class AuthorBaseRepository extends Repository<Author, Object>
```

`findById(...)`, `deleteById(...)`, `existsById(...)` nehmen alle `Object`.
Keine Compile-Zeit-Sicherheit auf dem Primärschlüssel —
`personRepo.findById("tippfehler")` kompiliert und wirft erst im Codec. Der Typ
ist zur Compile-Zeit trivial ableitbar (`@PartitionKey`-Feld); dass er
weggeworfen wird, ist die auffälligste API-Schwäche.

### E6 — Prepared-Statement-Explosion — dokumentiert, aber nicht gelöst

`toProperties` lässt null-Felder weg, also variiert der INSERT-Text mit dem
Befüllungsmuster. Bei 10 optionalen Feldern: bis zu 2^10 verschiedene
CQL-Strings, jeder mit eigenem PREPARE-Roundtrip gegen jeden Node. Bei 20M
writes/day kein theoretisches Problem.

Die README warnt korrekt (`README.md:540`) und schiebt die Verantwortung auf den
Nutzer. Der Driver kann das sauber: **fixer Spaltensatz +
`BoundStatementBuilder.unset()`** für null-Werte (Protocol v4). Ergebnis: genau
*ein* Prepared Statement pro Entity, keine Tombstones, dokumentiertes
Null-Verhalten bleibt erhalten.

### E7 — `LIMIT` wird interpoliert statt gebunden

```java
// Repository.java:139, :149, :328, :338 — dieselben vier Stellen reaktiv
String cql = String.format("SELECT * FROM %s %s LIMIT %d",
                           tableName, sortClause, pageable.size());
```

Ein Prepared Statement pro Page-Size. `LIMIT ?` binden.

### E8 — Converter werden pro Row und pro Feld neu allokiert

```java
// ConverterTypeHandler.java:53 — generiert in map() UND toProperties()
$T $L = new $T();   // new MyConverter() bei jeder Zeile, jedem Feld
```

Converter sind per Design zustandslos → `private static final` Feld in der
Mapper-Klasse.

Dazu in `EnumTypeHandler` und `ConverterTypeHandler`: `row.get(col, T.class)`
wird **zweimal** aufgerufen (Null-Check + Wert) — zwei Namens-Lookups und zwei
Decodes pro Feld pro Zeile. `EnumType.ORDINAL` ruft zusätzlich `values()` auf
(klont jedes Mal das Array) und hat keinen Bounds-Check.

### E9 — Entity-Mapper brechen bei Teilspalten-SELECTs

`map()` ruft `row.get(spalte, ...)` für **jedes** Entity-Feld. Jede `@Query`,
die eine Teilmenge selektiert und `returnType = LIST/SINGLE` auf die Entity
setzt, wirft zur Laufzeit `IllegalArgumentException`. Nicht dokumentiert, nicht
getestet — alle Test-Queries machen `SELECT *`.

### E10 — Kein Schutz gegen Event-Loop-Blocking

Das blockierende `Repository` ruft `session.execute()` direkt. Injiziert in eine
reaktive Route blockiert das den Event Loop. Kein `@Blocking`, keine Prüfung,
kein Hinweis in der README.

### E12 — `SELECT *` auf allen Kern-Lesepfaden — der Driver warnt aktiv davor

Nachgetragen am 2026-08-04 aus dem Testlauf; beim reinen Lesen nicht sichtbar.
Der ScyllaDB-Driver loggt bei **jedem** Prepared Statement der Extension:

```
WARN [DefaultPreparedStatement] Prepared statement SELECT * FROM book WHERE id = ?
is a wildcard select, which can cause prepared statement invalidation issues when
executed on CQL4. These issues may lead to broken deserialization or data corruption.
To mitigate this, the driver ensures that the server returns metadata with each query
for such statements, though this negatively impacts performance.
```

Betroffen ist die gesamte Kern-Lese-API: `findById`, `findByKeys`, `findAll`,
`findAll(Pageable, Sortable)`, `findAllPaged` — plus jede Nutzer-`@Query` mit
`SELECT *`. Zwei Konsequenzen:

1. **Korrektheit:** Ändert sich das Schema (ALTER TABLE ADD COLUMN) während
   Statements gecacht sind, droht laut Driver kaputte Deserialisierung.
2. **Performance:** Die Mitigation des Drivers ist, sich bei *jeder* Ausführung
   die Ergebnis-Metadaten mitschicken zu lassen. Genau auf dem heißesten Pfad
   einer 20M-writes/day-Anwendung wird also dauerhaft der langsame Pfad
   genommen.

Die Extension kennt alle Spalten zur Compile-Zeit — der Mapper generiert die
Liste ohnehin. Eine explizite Spaltenliste statt `*` beseitigt beide Probleme.

**Erledigt in Schritt 3.** Korrektur zu einer früheren Fassung dieses Absatzes:
das löst **E9 nicht mit**. E9 betrifft *nutzergeschriebenes* `@Query`-CQL, das
die Extension nicht umschreibt — dort bleibt die Einschränkung bestehen und ist
jetzt in der README dokumentiert.

### E11 — Zwei Konstruktions-Fallen aus CDI-Zwängen

```java
public Repository() {          // Repository.java:31
    this.session = null; this.tableName = null;
    this.mapper = null; this.registry = null;
}
```

Public — `new PersonBaseRepository()` liefert ein Objekt, bei dem jede Methode
NPEt. Sollte mindestens `protected` sein.

Die generierten Mapper sind `public final class` mit `@ApplicationScoped`. Das
funktioniert nur, weil ArC per Default `transform-unproxyable-classes=true` das
`final` per Bytecode-Rewrite entfernt. Flag umgestellt → Extension bricht.
`final` weglassen.

## Design-Schulden

### D1 — docs-Modul ist zu 100 % unverändertes Neo4j-OGM-Template

`docs/antora.yml` sagt `name: quarkus-neo4j-ogm`, `index.adoc` heißt
"= Quarkus Neo4j Ogm" und enthält noch `TIP: Describe what the extension does
here.` Wird bei jedem Nicht-Release-Build mitgebaut. Entweder ausfüllen oder
entfernen — die README (676 Zeilen, gut) macht die Arbeit ohnehin.

### D2 — `Paged.totalElements` ist immer `-1`

Ein Feld, das systematisch lügt, ist schlechter als kein Feld. Entfernen oder
korrekt füllen.

### D3 — ~40 Zeilen reine Overload-Duplikation je Repository

`query` / `querySingle` / `queryScalar` / `execute` / `queryProjection` je 4×.
Die Varargs-Variante deckt alles ab. Nebeneffekt:
`queryScalar(cql, meineFunctionVariable)` löst still auf die
`Object p1`-Überladung auf und bindet die Function als Query-Parameter.

### D4 — `Repository` und `ReactiveRepository` sind zu ~90 % dupliziert

`buildWhereClause`, `buildKeyParams`, `concat`, die gesamte CQL-Konstruktion je
zweimal. Der `StatementBinder` zeigt, dass das Muster bekannt ist — es ist nur
bei einer Methode geblieben.

### D5 — DDL-Guard verankert, Geschwister-Klassifizierer nicht

`isWrite` / `isSchema` / `isConditional`
(`QueryMethodFactory.java:267–282`) suchen unverankert im String.
`UPDATE book SET note = 'if you like' WHERE ...` wird als conditional
klassifiziert und bekommt den falschen Method-Body.

### D6 — `GeneratedValue.Strategy.SEQUENCE` ist tot

Existiert im Enum, wird nirgends implementiert, wird still ignoriert.

### D7 — `@SupportedSourceVersion(RELEASE_21)` bei `release=25`

In `EntityMapperProcessor.java`. → `SourceVersion.latestSupported()`.

### D8 — `registerConfigMapping` ist inkonsistent

Registriert `MetricsConfig` und `ThrottlerConfig` nicht. Bei `@ConfigMapping`
sind die Registrierungen vermutlich ohnehin überflüssig.

### D9 — `RepositoryRegistry.register` ist check-then-act

Statt `putIfAbsent` auf der `ConcurrentHashMap`.

### D10 — `EntityMapperProcessor` weist ein Feld in der Schleife zu

`mapperGenerator = new MapperGenerator()` — sollte lokal sein.

### D11 — Parent-POM hat `<tag>v1.0.0</tag>` bei Version `1.0.10`

Release-Metadaten sind verrutscht.

### D12 — `ALLOW FILTERING` in den eigenen Beispiel-Entities

`integration-tests/.../model/Author.java`. Als kanonisches Beispiel im eigenen
Testcode ein schlechtes Vorbild für eine Prod-orientierte Library.

### D15 — `byte[]`-Felder werden nicht unterstützt

Nachgetragen aus Schritt 2. Der Mapper generiert `row.get(col, byte[].class)`; der
Driver hat nur einen `BLOB <-> ByteBuffer`-Codec →
`CodecNotFoundException: [BLOB <-> [B]`. Anders als `LocalDateTime` ist die
Umrechnung hier eindeutig (`ByteBuffer.wrap` / `remaining()`-Kopie) und gehört in
einen `TypeHandler`, analog zu `EnumTypeHandler`. Bis dahin: README dokumentiert
es als nicht unterstützt, `MappingLimitationsTest` nagelt es fest.

### D14 — `maven-gpg-plugin` hängt unbedingt an `verify`

Im Parent-POM unter `<build><plugins>` statt im `release`-Profil. Jeder
`mvn verify` versucht zu signieren; ohne Key bricht der Build. Gehört ins
`release`-Profil, das der `maven-release-plugin` ohnehin via `releaseProfiles`
aktiviert. Aufgefallen bei der CI-Einrichtung (Schritt 1), dort mit
`-Dgpg.skip=true` umgangen.

Kleiner Nachbar-Befund aus demselben Build-Log: der `quarkus-maven-plugin`
läuft ohne `<extensions>true</extensions>` und warnt bei jedem Build, dass er
essentielle Build-Settings deshalb nicht prüfen kann.

### D13 — Keyspace ist compile-time gebacken

`@Table(keyspace=...)` überstimmt `quarkus.scylla.keyspace`. Kein
Keyspace-per-Environment / -per-Tenant ohne Rebuild. Bekannt und akzeptiert —
hier nur zur Vollständigkeit festgehalten.
